## Finding 1 — Save tamper-reset is a no-op against the per-class wallets it checksums (real logic bug)

- **Files:** `src/access/saveIntegrity.js:50-70`, `BossRush.jsx:1221-1227`
- **Root cause:** `computeSaveChecksum` sums **per-class** wallets via `totalWallet(save)` which reads `save.classes[*].wallet` (line 24-32). But the mismatch branch of `verifySaveIntegrity` (lines 59-69) resets only a **top-level** `save.wallet` and `save.records` — a field that no longer exists in current saves (the v1.0.7 migration at `BossRush.jsx:1139-1141` drops the old global `data.wallet`, and reads go through `walletForClass` → `save.classes[classKey].wallet`, `BossRush.jsx:985`).
- **Why it's failing:** On a checksum mismatch the function leaves every `save.classes[*].wallet` untouched, then recomputes the checksum over those same (possibly tampered) values and re-blesses them. The "reset" clears only the aggregate `records` counters; the thing the checksum is meant to deter (edited per-class coin balances / best floor) survives intact. The deterrent is effectively defeated.

## Finding 2 — Cloud save/load ignores Supabase errors → silent data loss, false success

- **File:** `api/sync-save.js:116-126` (GET) and `api/sync-save.js:155-161` (POST)
- **Root cause:** `await supabase.from("profiles").upsert({...})` discards the returned `{ error }` and unconditionally returns `{ ok: true }`. The GET similarly destructures `{ data }` and swallows any error, returning `save_data: null` as if the user had no save.
- **Why it's failing/suboptimal:** A write that fails at the DB layer (RLS rejection, constraint, transient outage) reports success to the client, so the player believes their progress is backed up to the cloud when it was not. The GET masks a read error as "no cloud save," which can trigger an unwanted overwrite with local/empty data.

## Finding 3 — `respecClass` zeroes `spBoost` that `computeRespecRefund` never refunds (latent trap)

- **Files:** `BossRush.jsx:2731-2760` (resets `spBoost: 0`), `BossRush.jsx:947-964` (refund excludes `spBoost`, per the doc comment at line 945)
- **Root cause:** Respec resets `hpBoost/atkBoost/defBoost/spBoost` and all `skillLevels`, but the refund total only sums hp/atk/def + skillLevels. `spBoost` is reset without being refunded.
- **Why it's suboptimal (not yet a live bug):** There is currently **no** `buySpBoost` path (only `buyHpBoost/buyAtkBoost/buyDefBoost` and `buySkillUpgrade`), so `spBoost` is always 0 and the mismatch is harmless today. But it is a correctness trap: the moment an SP-boost purchase is added, respec will silently destroy paid SP upgrades without refunding the coins. Either stop resetting `spBoost`, or include it in the refund.

## 🎯 Developer Prompt 1 — Save integrity reset

**Context Files to reference:**
- `src/access/saveIntegrity.js`
- `BossRush.jsx` (load path at `loadSave`, ~line 1221; `walletForClass`, ~line 985)

**The Issue:**
On a save-checksum mismatch, `verifySaveIntegrity` resets a vestigial top-level `save.wallet` and `save.records`, but never resets the per-class `save.classes[*].wallet` values that `computeSaveChecksum` actually sums — so tampered per-class wallets survive the "reset" and get re-blessed into a fresh checksum.

**Error Details / Code Snippet:**
```js
// src/access/saveIntegrity.js — mismatch branch
const reset = {
  ...save,
  wallet: 0,                                   // no current code reads top-level save.wallet
  records: { coins: 0, streak: 0, rounds: 0 }, // per-class wallets left untouched
  _saveChecksum: computeSaveChecksum({ ...save, wallet: 0, records: {...} }),
};
// but computeSaveChecksum → totalWallet(save) reads save.classes[*].wallet
```

**Proposed Fix Strategy:**
1. In the reset branch, build `reset.classes` by mapping every entry of `save.classes` to `{ ...meta, wallet: 0 }` so the per-class wallets the checksum covers are actually zeroed.
2. Recompute `_saveChecksum` over that fully-reset object (zeroed per-class wallets + zeroed records + preserved bestFloor/purchased).
3. Drop the meaningless top-level `wallet: 0` (or keep it, but it must not be mistaken for the source of truth).
4. Add/extend a test under `tools/` (mirror `save-meta-test.mjs`) that tampers a `classes.*.wallet`, runs `verifySaveIntegrity`, and asserts the returned save's per-class wallets are 0 and `ok === false`.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align with the existing architectural patterns in the repository and do not break adjacent dependencies. Keep this a deterrent (not a security boundary) per the module's doc comment; don't over-engineer. Run `node tools/save-meta-test.mjs` and the full `tools/*-test.mjs` suite plus `npm run build` before finishing.

## 🎯 Developer Prompt 2 — Cloud sync error handling

**Context Files to reference:**
- `api/sync-save.js`
- `src/access/cloudSave.js` (client caller — confirm how it interprets `{ ok: true }` / `save_data: null`)

**The Issue:**
`api/sync-save.js` ignores the `{ error }` returned by Supabase on both the POST upsert and the GET select, so a failed DB write still returns `{ ok: true }` (false success → silent loss of cloud backup) and a failed read returns `save_data: null` (masked as "no save").

**Error Details / Code Snippet:**
```js
// POST
await supabase.from("profiles").upsert({ id: userId, save_data: saveData, updated_at: ... });
return json(res, 200, { ok: true });            // error never checked

// GET
const { data } = await supabase.from("profiles").select("save_data, purchased").eq("id", userId).maybeSingle();
return json(res, 200, { save_data: data?.save_data ?? null, purchased: Boolean(data?.purchased) });  // error swallowed
```

**Proposed Fix Strategy:**
1. Capture `const { error } = await supabase...upsert(...)` and, if `error`, return `json(res, 500, { error: "save_failed" })` instead of `{ ok: true }`.
2. Capture `error` on the GET select; on error return a 500 (`{ error: "load_failed" }`) so the client can distinguish "read failed" from "no save," rather than defaulting to `null`.
3. On the client (`cloudSave.js`), make sure a non-OK sync response does not surface as "backed up" and a load error does not overwrite local progress with empty data.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align with the existing architectural patterns in the repository (the `json()` helper, existing status-code conventions like 429/413/403) and do not break adjacent dependencies. Do not log or leak Supabase internals to the client. Verify `npm run build` still passes.

## 🎯 Developer Prompt 3 — Respec / spBoost consistency

**Context Files to reference:**
- `BossRush.jsx` (`respecClass`, ~line 2731; `computeRespecRefund`, ~line 947)

**The Issue:**
`respecClass` resets `spBoost` to 0 but `computeRespecRefund` deliberately excludes `spBoost` from the refund. It is harmless today because nothing ever increments `spBoost` (there is no `buySpBoost`), but it is a latent trap: adding an SP-boost purchase later would make respec silently destroy paid SP upgrades without refunding coins.

**Error Details / Code Snippet:**
```js
// respecClass resets spBoost:
const nextMeta = { ...meta, hpBoost: 0, atkBoost: 0, defBoost: 0, spBoost: 0, skillLevels: resetSkills, wallet: newWallet };
// computeRespecRefund sums only hpBoost/atkBoost/defBoost + skillLevels — "Weapons and spBoost are excluded."
```

**Proposed Fix Strategy:**
1. Decide the invariant: either (a) `spBoost` is permanently non-purchasable — then stop resetting it in `respecClass` (leave `meta.spBoost` as-is) so respec only touches refundable upgrades; or (b) `spBoost` will become purchasable — then include it in `computeRespecRefund` (sum `spPrice(i)` for `i < spBoost`, combo-scaled via `shopPriceForClass`) so the refund stays exact.
2. Keep refund arithmetic exact (prices are deterministic; the sum must equal coins paid, combo ×3 included).
3. Add a quick assertion/test that respec refund equals total spent for a class with mixed stat + skill levels.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Pick option (a) unless an SP-boost shop item is actually planned. Ensure that your changes align with the existing architectural patterns in the repository and do not break adjacent dependencies. Run the `tools/*-test.mjs` suite and `npm run build`.
