**🎯 Developer Prompt**

**Context Files to reference:**

**The Issue:**
Two independent bugs. (1) The save tamper-reset in `verifySaveIntegrity` was never updated for the v1.0.7 per-class-wallet migration, so it fails to neutralize tampered coins *and* destroys legitimate records. (2) The Stripe webhook and the save-sync endpoint ignore the Supabase write result and always return success, so a failed DB write silently drops a paid purchase (or a save).

**Error Details / Code Snippet:**

_Bug 1 — `src/access/saveIntegrity.js:34–69`_
```js
export function computeSaveChecksum(save) {
  const payload = {
    wallet: totalWallet(save),        // sum of save.classes[*].wallet
    rounds: Number(save?.records?.rounds) || 0,
    coins: Number(save?.records?.coins) || 0,
    bestFloor: accountBestFloor(save),
    purchased: Boolean(save?.purchased),
  };
  return fnv1a(JSON.stringify(payload));
}

export function verifySaveIntegrity(save) {
  ...
  const reset = {
    ...save,                                   // keeps save.classes[*].wallet (tampered) intact
    wallet: 0,                                 // top-level wallet — the game never reads this post-migration
    records: { coins: 0, streak: 0, rounds: 0 }, // wipes legit lifetime records
    _saveChecksum: computeSaveChecksum({ ...save, wallet: 0, records: { coins: 0, streak: 0, rounds: 0 } }),
  };
  return { ok: false, save: reset };           // re-stamps tampered per-class coins with a VALID checksum
}
```
Root cause: `computeSaveChecksum` sums per-class wallets (`save.classes[*].wallet`), but the reset branch zeroes a non-existent top-level `save.wallet` (dropped during the v1.0.7 migration — see `BossRush.jsx:1139–1141`). Net effect on a mismatch: tampered coins survive and get a fresh valid checksum (deterrent defeated), while the player's untouched lifetime `records` are wiped (false-positive data loss).

_Bug 2 — `api/stripe-webhook.js:50–58`_
```js
await supabase.from("profiles").upsert({
  id: userId, purchased: true, updated_at: new Date().toISOString(),
});                       // result.error never checked
...
return json(res, 200, { received: true });  // 200 even if the upsert failed
```
Root cause: the `{ error }` returned by `upsert` is discarded. If the write fails, Stripe receives `200` and never retries, so a paid user is never marked `purchased`. Same pattern in `api/sync-save.js:155` (POST upsert → `200 { ok: true }` regardless of DB error).

**Proposed Fix Strategy:**
1. In `verifySaveIntegrity`, make the reset actually zero what the checksum covers: zero each `save.classes[*].wallet` (not top-level `wallet`), then recompute the checksum from that same object so tampered coins are genuinely neutralized. Only wipe `records` if the records themselves fail validation — don't zero legit lifetime stats as collateral for a wallet-only mismatch.
2. Add a focused regression test (mirroring `tools/save-meta-test.mjs`) that tampers a single class's `wallet`, runs `verifySaveIntegrity`, and asserts (a) the returned save's per-class wallets are reset and (b) the new checksum verifies, and that an untampered save with valid records keeps its `records`.
3. In `api/stripe-webhook.js`, capture `const { error } = await supabase...upsert(...)`; on error, log it and return a `500` so Stripe retries the webhook (keep the existing `200 { received: true }` only on success and for event types you intentionally ignore).
4. In `api/sync-save.js`, capture the upsert `error` on the POST path and return `500 { error: "save_failed" }` on failure instead of `200 { ok: true }`.
