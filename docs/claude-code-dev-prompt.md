## 🎯 Developer Prompt (copy everything below into Claude Code)

**Context Files to reference:**
- `src/access/saveIntegrity.js`
- `BossRush.jsx` (the `loadSave()` path around lines 1221–1227 that calls `verifySaveIntegrity`)

**The Issue:**
The save-tamper "reset" in `verifySaveIntegrity()` zeroes the wrong field. It resets a legacy top-level `save.wallet` (unused since v1.0.7) and `save.records`, but the actual coins now live in per-class wallets at `save.classes[*].wallet`. So when a tampered save is detected, the cheated coins survive untouched **and** the function re-signs the save with a fresh valid checksum — effectively laundering the tamper instead of undoing it. The checksum is explicitly a deterrent, not security, but right now it fails at the one value it most visibly protects.

**Error Details / Code Snippet:**

Reproduced (stub `import.meta.env.DEV` → `false` so it runs under Node):
```
tamper detected (ok=false):                       true
warrior wallet AFTER reset:                       1000000000   (expected 0)
top-level save.wallet after reset:                0            (the field it actually zeroes — unused)
reset save passes re-check (re-blesses the cheat): true
```

Offending reset block — `src/access/saveIntegrity.js:50–70`:
```js
export function verifySaveIntegrity(save) {
  if (!save || typeof save !== "object") return { ok: false, save: null };
  const expected = save._saveChecksum;
  if (!expected) return { ok: true, save };
  const actual = computeSaveChecksum(save);
  if (actual === expected) return { ok: true, save };
  if (import.meta.env.DEV) {
    console.warn("[save] checksum mismatch — resetting wallet/records");
  }
  const reset = {
    ...save,
    wallet: 0,                                   // ← legacy top-level field; NOT where coins live
    records: { coins: 0, streak: 0, rounds: 0 },
    _saveChecksum: computeSaveChecksum({         // ← re-blesses the still-tampered classes[*].wallet
      ...save,
      wallet: 0,
      records: { coins: 0, streak: 0, rounds: 0 },
    }),
  };
  return { ok: false, save: reset };
}
```
Note `computeSaveChecksum` derives its wallet term from `totalWallet(save)` = the sum of `save.classes[*].wallet` (see lines 24–43), which the reset never modifies.

**Secondary issue in the same function:** `import.meta.env.DEV` throws `TypeError: Cannot read properties of undefined (reading 'DEV')` if this function is ever called outside a Vite bundle (e.g. a Node-based test/tool touching the mismatch path). It's safe in the deployed app because Vite statically replaces it, but it makes the branch untestable from plain Node.

**Proposed Fix Strategy:**
1. In the reset branch, rebuild the save so the **per-class wallets** are actually zeroed: map over `save.classes` and set each `meta.wallet = 0` (keep every other per-class field — `hpBoost`, `skillLevels`, `bestFloorReached`, etc. — intact; this is an anti-cheat reset, not a progress wipe). Drop the dead top-level `wallet: 0` write (or keep it harmlessly, but it must not be the only thing reset).
2. Compute the new `_saveChecksum` from that same wallet-zeroed object so the re-signed save reflects the corrected state (zeroed wallets), not the tampered one.
3. Guard the dev log so it can't throw outside Vite, e.g. `if (import.meta.env?.DEV)` or `if (typeof import.meta.env !== "undefined" && import.meta.env.DEV)`.
4. Add a focused regression test (mirror the style of `tools/save-meta-test.mjs`): attach a checksum to a save with `classes.warrior.wallet = 100`, tamper it to `1_000_000_000`, run `verifySaveIntegrity`, and assert (a) `ok === false`, (b) the returned `save.classes.warrior.wallet === 0`, and (c) re-running `verifySaveIntegrity` on the returned save is now consistent. Wire it into the AGENTS.md test list.
