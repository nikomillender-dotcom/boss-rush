## 🎯 Developer Prompt #1 — Tamper-reset doesn't reset per-class wallets (HIGH)

**Context Files to reference:**
- `src/access/saveIntegrity.js`
- `BossRush.jsx` (save load at ~line 1160–1255; per-class `wallet` lives in `save.classes[*].wallet`)

**The Issue:**
`verifySaveIntegrity()` is the client-side save tamper deterrent, but its reset branch zeroes a
legacy top-level `save.wallet` field that the checksum no longer uses, while leaving the real
per-class wallets (`save.classes[*].wallet`) untouched. Since v1.0.7 moved coins to per-class
wallets (and `computeSaveChecksum` sums them via `totalWallet`), the "reset" doesn't actually
reset the tampered coins — and the half-reset blob is then re-blessed into a valid checksum,
permanently laundering the cheat.

**Error Details / Code Snippet:**
`src/access/saveIntegrity.js` lines 59–69:
```js
const reset = {
  ...save,
  wallet: 0,                                   // <-- top-level field NOT used by the checksum
  records: { coins: 0, streak: 0, rounds: 0 }, // records reset OK
  _saveChecksum: computeSaveChecksum({ ...save, wallet: 0, records: { coins: 0, streak: 0, rounds: 0 } }),
};
return { ok: false, save: reset };
```
Reproduction (confirmed): tamper `classes.warrior.wallet` 500 → 999999 with the old checksum.
`verifySaveIntegrity` detects the mismatch (`ok: false`) but returns a "reset" save whose
`classes.warrior.wallet` is still `999999`, and `attachSaveChecksum(reset)` then validates as `ok: true`.

**Proposed Fix Strategy:**
1. In the reset branch, zero the per-class wallets too — map over `save.classes` and set each
   `meta.wallet = 0` (and reconsider whether `megaBossKills`/records-derived fields that feed the
   checksum should also be reset).
2. Drop or keep the obsolete top-level `wallet: 0` only if some legacy path still reads it; the
   checksum reset must cover exactly the fields `computeSaveChecksum` hashes (`totalWallet`,
   `records.rounds`, `records.coins`, `accountBestFloor`, `purchased`).
3. Add a case to `tools/save-meta-test.mjs` (or a new `save-integrity-test.mjs`) that tampers a
   per-class wallet and asserts the returned save has that wallet zeroed and re-checksums clean.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align
with the existing architectural patterns in the repository and do not break adjacent dependencies.

## 🎯 Developer Prompt #2 — Stripe webhook swallows DB-write failure, returns 200 (HIGH, money path)

**Context Files to reference:**
- `api/stripe-webhook.js`

**The Issue:**
On `checkout.session.completed`, the handler upserts `purchased: true` but never checks the
upsert result. If the Supabase write fails, the error is silently discarded and the handler still
returns `200 { received: true }`, so Stripe marks the webhook delivered and never retries — the
customer pays but their account is never unlocked.

**Error Details / Code Snippet:**
`api/stripe-webhook.js` lines 50–58:
```js
await supabase.from("profiles").upsert({
  id: userId,
  purchased: true,
  updated_at: new Date().toISOString(),
});            // <-- { error } never inspected
// ...
return json(res, 200, { received: true });
```

**Proposed Fix Strategy:**
1. Destructure `{ error }` from the upsert and, when it is set, `console.error` it and return a 5xx
   (e.g. `json(res, 500, { error: "db_write_failed" })`) so Stripe retries the webhook.
2. Keep returning 200 for event types you intentionally ignore, and for a missing `userId` (log it
   so it's visible), so you don't trigger infinite retries on unactionable events.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align
with the existing architectural patterns in the repository and do not break adjacent dependencies.

## 🎯 Developer Prompt #3 — Cloud save reports success even when the write failed (MEDIUM)

**Context Files to reference:**
- `api/sync-save.js`
- `src/access/cloudSave.js`

**The Issue:**
Two swallowed-failure spots on the cloud-save path: (a) `api/sync-save.js` upserts the save blob
without checking the result, then returns `{ ok: true }` unconditionally; (b) `src/access/cloudSave.js`
`syncProgressToCloud` never checks the `fetch` response status, so a 403 (`not_purchased`),
429 (`rate_limited`), or 5xx is treated as a successful sync. Progress can silently fail to persist
to the cloud while the client believes it saved.

**Error Details / Code Snippet:**
`api/sync-save.js` lines 155–161:
```js
await supabase.from("profiles").upsert({ id: userId, save_data: saveData, updated_at: ... });
return json(res, 200, { ok: true });   // <-- upsert error never checked
```
`src/access/cloudSave.js` lines 19–26:
```js
await fetch("/api/sync-save", { method: "POST", ... });  // <-- res.ok never inspected
```

**Proposed Fix Strategy:**
1. In `api/sync-save.js`, capture `{ error }` from the upsert; on error return a 5xx instead of
   `{ ok: true }`.
2. In `cloudSave.js`, check `res.ok` and surface/log non-OK responses; optionally keep the pending
   save for a later retry rather than discarding it.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align
with the existing architectural patterns in the repository and do not break adjacent dependencies.
