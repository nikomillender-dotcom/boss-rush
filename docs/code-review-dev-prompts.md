## 🎯 Developer Prompt #1 — Tamper-reset doesn't reset per-class wallets (HIGH)

**Context Files to reference:**
- `src/access/saveIntegrity.js`
- `BossRush.jsx` (save load at ~line 1160–1255; per-class `wallet` lives in `save.classes[*].wallet`)

**The Issue:**
`verifySaveIntegrity()` is the client-side save tamper deterrent, but its reset branch zeroes a
legacy top-level `save.wallet` field that the checksum no longer uses, while leaving the real
per-class wallets (`save.classes[*].wallet`) untouched. Since v1.0.7 moved coins to per-class
wallets (and `computeSaveChecksum` sums them via `totalWallet`), the "reset" doesn't actually
reset the tampered coins — and the half-reset blob is then re-blessed into a valid checksum,
permanently laundering the cheat.

**Error Details / Code Snippet:**
`src/access/saveIntegrity.js` lines 59–69:
```js
const reset = {
  ...save,
  wallet: 0,                                   // <-- top-level field NOT used by the checksum
  records: { coins: 0, streak: 0, rounds: 0 }, // records reset OK
  _saveChecksum: computeSaveChecksum({ ...save, wallet: 0, records: { coins: 0, streak: 0, rounds: 0 } }),
};
return { ok: false, save: reset };
```
Reproduction (confirmed): tamper `classes.warrior.wallet` 500 → 999999 with the old checksum.
`verifySaveIntegrity` detects the mismatch (`ok: false`) but returns a "reset" save whose
`classes.warrior.wallet` is still `999999`, and `attachSaveChecksum(reset)` then validates as `ok: true`.

**Proposed Fix Strategy:**
1. In the reset branch, zero the per-class wallets too — map over `save.classes` and set each
   `meta.wallet = 0` (and reconsider whether `megaBossKills`/records-derived fields that feed the
   checksum should also be reset).
2. Drop or keep the obsolete top-level `wallet: 0` only if some legacy path still reads it; the
   checksum reset must cover exactly the fields `computeSaveChecksum` hashes (`totalWallet`,
   `records.rounds`, `records.coins`, `accountBestFloor`, `purchased`).
3. Add a case to `tools/save-meta-test.mjs` (or a new `save-integrity-test.mjs`) that tampers a
   per-class wallet and asserts the returned save has that wallet zeroed and re-checksums clean.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align
with the existing architectural patterns in the repository and do not break adjacent dependencies.

## 🎯 Developer Prompt #2 — Stripe webhook swallows DB-write failure, returns 200 (HIGH, money path)

**Context Files to reference:**
- `api/stripe-webhook.js`

**The Issue:**
On `checkout.session.completed`, the handler upserts `purchased: true` but never checks the
upsert result. If the Supabase write fails, the error is silently discarded and the handler still
returns `200 { received: true }`, so Stripe marks the webhook delivered and never retries — the
customer pays but their account is never unlocked.

**Error Details / Code Snippet:**
`api/stripe-webhook.js` lines 50–58:
```js
await supabase.from("profiles").upsert({
  id: userId,
  purchased: true,
  updated_at: new Date().toISOString(),
});            // <-- { error } never inspected
// ...
return json(res, 200, { received: true });
```

**Proposed Fix Strategy:**
1. Destructure `{ error }` from the upsert and, when it is set, `console.error` it and return a 5xx
   (e.g. `json(res, 500, { error: "db_write_failed" })`) so Stripe retries the webhook.
2. Keep returning 200 for event types you intentionally ignore, and for a missing `userId` (log it
   so it's visible), so you don't trigger infinite retries on unactionable events.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align
with the existing architectural patterns in the repository and do not break adjacent dependencies.

## 🎯 Developer Prompt #3 — Cloud save reports success even when the write failed (MEDIUM)

**Context Files to reference:**
- `api/sync-save.js`
- `src/access/cloudSave.js`

**The Issue:**
Two swallowed-failure spots on the cloud-save path: (a) `api/sync-save.js` upserts the save blob
without checking the result, then returns `{ ok: true }` unconditionally; (b) `src/access/cloudSave.js`
`syncProgressToCloud` never checks the `fetch` response status, so a 403 (`not_purchased`),
429 (`rate_limited`), or 5xx is treated as a successful sync. Progress can silently fail to persist
to the cloud while the client believes it saved.

**Error Details / Code Snippet:**
`api/sync-save.js` lines 155–161:
```js
await supabase.from("profiles").upsert({ id: userId, save_data: saveData, updated_at: ... });
return json(res, 200, { ok: true });   // <-- upsert error never checked
```
`src/access/cloudSave.js` lines 19–26:
```js
await fetch("/api/sync-save", { method: "POST", ... });  // <-- res.ok never inspected
```

**Proposed Fix Strategy:**
1. In `api/sync-save.js`, capture `{ error }` from the upsert; on error return a 5xx instead of
   `{ ok: true }`.
2. In `cloudSave.js`, check `res.ok` and surface/log non-OK responses; optionally keep the pending
   save for a later retry rather than discarding it.

## 🎯 Developer Prompt #4 — Unguarded `localStorage.setItem` blanks the app on mobile Safari (HIGH)

**Context Files to reference:**
- `BossRush.jsx` — `persistSave` (~line 1251), `loadSave` (~line 1247), `saveEffectsMode` (~line 1603)

**The Issue:**
`persistSave()` calls `localStorage.setItem` with no try/catch, unlike its sibling `saveEffectsMode`
which deliberately wraps the write for "private mode / storage disabled". `loadSave()` calls
`persistSave(save)` at line 1247 — outside the surrounding try/catch — from inside the `useState`
initializer in `useGameEngine`. In Safari Private Mode (and other storage-blocked contexts) `setItem`
throws `QuotaExceededError`, the throw escapes render, and the whole component fails to mount: a blank
screen. This is exactly the "doesn't work on phone" failure class the project already fights. The same
unguarded write is also reached at runtime via `commitSave` (addWallet/spendWallet/processVictory).

**Error Details / Code Snippet:**
`BossRush.jsx` lines 1251–1254:
```js
function persistSave(save) {
  const withChecksum = attachSaveChecksum(save);
  localStorage.setItem(META_SAVE_KEY, JSON.stringify(withChecksum)); // no try/catch — throws in private mode
  return withChecksum;
}
```
Compare the guarded sibling at lines 1603–1608 (`saveEffectsMode`).

**Proposed Fix Strategy:**
1. Wrap the `setItem` in `persistSave` in try/catch (mirror `saveEffectsMode`); still return
   `withChecksum` so in-memory state stays correct when the disk write fails.
2. Audit the other direct `localStorage` writes in `BossRush.jsx` for the same gap and route them
   through a single guarded helper.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align
with the existing architectural patterns in the repository and do not break adjacent dependencies.

## 🎯 Developer Prompt #5 — Reflect-kill race double-schedules victory + a fresh player turn (MEDIUM)

**Context Files to reference:**
- `BossRush.jsx` — `processEnemyTurn` Aegis/reflect branch (~lines 2518–2540), `enemyRef` assignment (~line 1704)

**The Issue:**
In the reflect-damage branch, `setEnemy(prev => ...)` schedules `processVictory()` when the reflected
damage kills the enemy, but a `queueMicrotask` immediately after reads `enemyRef.current` — which is
only assigned during render and therefore still holds the pre-reflect (alive) enemy. The microtask
takes the "enemy still alive" path and calls `beginPlayerTurn()`, queuing an AUTO command against a
dying enemy while the victory/floor-transition is also queued. Separately, the branch performs side
effects (`clearAllTimers`, `schedule(... processVictory)`) inside the `setEnemy` updater, which
violates React purity and double-fires `processVictory` under StrictMode in dev.

**Error Details / Code Snippet:**
`BossRush.jsx` ~lines 2518–2530:
```js
setEnemy((prev) => {
  const reflectedHp = Math.max(0, prev.hp - reflectDmg);
  if (reflectedHp <= 0) { clearAllTimers(); schedule(..., () => processVictory()); } // side effects in updater
  return { ...prev, hp: reflectedHp };
});
queueMicrotask(() => {
  const currentFoe = enemyRef.current;            // STALE: pre-reflect hp > 0
  if (currentFoe && currentFoe.hp <= 0) { finishEnemyTurn(); return; }
  ... beginPlayerTurn();                          // runs even though the enemy just died
});
```

**Proposed Fix Strategy:**
1. Compute `reflectedHp` once before `setEnemy`, decide victory-vs-continue from that local value
   (not from `enemyRef.current`), and drive the branch off it in the microtask too.
2. Move the `clearAllTimers`/`schedule(processVictory)` side effects out of the `setEnemy` updater to
   after the state call, so the updater is pure and not double-invoked by StrictMode.

**Instructions for Developer:**
Review the identified issue and implement the proposed fix strategy. Ensure that your changes align
with the existing architectural patterns in the repository and do not break adjacent dependencies.

## 🎯 Developer Prompt #6 — Persistence / cloud-sync side effects run inside a state updater (MEDIUM)

**Context Files to reference:**
- `BossRush.jsx` — `addWallet` (~lines 1908–1913), `commitSave` (~line 1800)

**The Issue:**
The `setWallet(prev => ...)` updater in `addWallet` mutates `walletRef.current` and calls
`commitSave(...)` (which does a `localStorage` write + `setSave` + `scheduleCloudSync`). State
updaters must be pure; under StrictMode (dev) this updater runs twice → double persistence and double
cloud-sync scheduling, and it is also where the unguarded `persistSave` from Prompt #4 can throw
during render.

**Error Details / Code Snippet:**
`BossRush.jsx` lines 1908–1913:
```js
setWallet((prev) => {
  const next = prev + amount;
  walletRef.current = next;                                        // ref mutation in updater
  if (key) commitSave(setClassWallet(saveRef.current, key, next)); // persist + cloud sync in updater
  return next;
});
```

**Proposed Fix Strategy:**
1. Compute `next` outside the updater (from `walletRef.current`/`saveRef.current`), call
   `setWallet(next)`, then update the ref and call `commitSave` once after the state call.
2. Apply the same pattern to any other updater in the file that performs persistence or scheduling.

## 🎯 Developer Prompt #7 — Untracked visual timers + stale `turn` guards (LOW, consistency)

**Context Files to reference:**
- `BossRush.jsx` — `spawnFloat`/`triggerShake`/`triggerFlash`/`triggerStreakPop`/`triggerCoinPop`
  (~lines 2225–2253), `clearAllTimers` (~line 1767); AUTO action guards in `actionFight`/`actionDefend`/
  `actionRetreat`/`actionMagic` (~lines 3015, 3020, 3038, 3076)

**The Issue:**
Two low-severity consistency hazards: (a) the visual-effect helpers use bare `setTimeout` whose IDs are
never pushed into `timersRef`, so `clearAllTimers()` and the unmount cleanup never cancel them — they
can fire `setState` after unmount or after a scene reset (`actionRetreat`/`startGame`). (b) The four
AUTO action functions guard on the destructured `turn` state (`if (turn !== "player") return;`) while
the rest of the AUTO chain correctly uses `turnRef.current`; captured in a stale closure, these can
disagree with the ref and risk a silent AUTO stall.

**Proposed Fix Strategy:**
1. Route the visual-effect `setTimeout`s through the tracked `schedule()` helper (or push their IDs into
   `timersRef`) so they are cancelled by `clearAllTimers()`.
2. Change the four AUTO action guards to read `turnRef.current` to match the rest of the engine.
